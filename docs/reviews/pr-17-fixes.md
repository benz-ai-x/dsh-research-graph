## 实际 Chrome 路径

1. 对来源的三个完整轮次提炼，第一张草稿引用第 1、2 轮。人工改写结论后，从引用阅读器选择第 2 轮再次提炼：新操作先要求预览，实际只纳入事件 20–26；关闭后，原草稿的人工结论仍在。
2. 保存第一张卡，重新编辑时第 1、2 轮保持勾选。增加第 3 轮、保存后再取消第 2 轮。Host 中三个修订的引用分别为 `[1,2]`、`[1,2,3]`、`[1,3]`，旧修订未改写。
3. 从该卡来源阅读器选择第 2 轮并新建“独立新卡：第二轮来源”。表单为空白新卡；保存后的卡片 ID 与原卡不同，只有事件 20–26。关闭后返回原卡。
4. 将原卡 Revision 3 加入材料，选择另一个“验证工作区”并预览。模拟原生 Host 已接收后提交响应丢失，且随后的恢复读取也失败。问题、工作区、移除材料和重新预览均禁用；页面保留目标 ID、“Check target status”和同次重试入口。
5. 点击核对恢复 accepted 状态，预览保持 1,030 字符且逐字相同。明确点击打开目标后，材料记录、原生用户消息与预览一致；只有一个带原生 `rpcId` 的用户请求，且等于记录的 `requestId`。宿主另外提供的运行上下文消息不计为该用户请求。
6. 重启同一个隔离 Host，再从实际页面读取目标材料。两张卡及其修订、沿用记录、三个源会话的所有事件均相同；目标仍只有一个原生用户请求，重启后的读取调用模型 0 次。

取消和迟到响应的组合由正式 UI／Host 回归验证；此次浏览器故障注入覆盖已接收后的连续两次响应失败及主动恢复，没有将它记为完整网络断开实验。

三个源会话分别有 37、36、36 条事件，操作前后完整快照 hash 相同，跨 Host 重启逐条事件相同。本轮只使用固定响应模型：来源准备含标题共 12 次，操作前重启将计数清零；两次提炼及新讨论／标题共 4 次，恢复读取未增加计数。未调用真实提供方，未复制模型凭据。此前真实模型质量样例仍见[独立记录](issues-6-10-model-quality.md)。浏览器 `pageerror` 为 0。
